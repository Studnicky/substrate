`timeoutMs` bounds task execution only — its clock starts once a worker has finished starting, immediately before the item is posted, never while the worker is still booting. A new, independently optional `startupTimeoutMs` bounds worker startup itself (`WorkerPool`'s `'online'` event; `WebWorkerPool`'s factory `create()`/`initialize()`), has no default (a pool given neither timeout runs with no deadline in either phase, exactly like `timeoutMs` alone used to), and rejects with one of three distinct, accurate messages depending on what actually happened: a caller cancellation mid-startup (`cancelled before its worker finished starting`), a genuinely elapsed startup deadline (`did not finish starting within its startup timeout`), or a signal already aborted before startup began (`was not dispatched because its signal was already aborted`) — never the task-timeout message, and reported through `onWorkerError`, not `onWorkerTimeout`. A caller-supplied `abortSignal` is composed exactly once per task; the startup and task deadlines are independent timers derived from that single composition, so the caller's signal carries exactly one abort listener for the task's entire lifetime and cancels it correctly during either phase.
